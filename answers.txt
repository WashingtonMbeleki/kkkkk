=== Question 1.1 ===
Waterfall is a phased, sequential model: requirements are frozen up front, then design, build, test, and release happen in fixed stages. Agile is time-boxed delivery in short iterations: the team works in small slices, keeps the product releasable, and re-prioritises as feedback arrives.

Salesforce's problems were the classic signs of a phase-based process growing too large: long lead times, late discovery of problems, smaller and less predictable releases, and difficulty forecasting what would be in a release. When an organisation scales, large upstream decisions become stale, dependencies pile up, and testing is delayed until the end. Short time-boxed iterations reduce this by forcing regular review, faster feedback, and smaller batches of work that can be planned, built, and checked quickly. That makes delivery more predictable and keeps the product releasable.

=== Question 1.2 ===
I would set a basic operating process with a few guardrails:

1. A backlog with clear work items and priorities. Each item has an owner, brief description, acceptance criteria, and status. This prevents work being picked up informally or disappearing into “someone is doing it.”
2. A time-boxed sprint or iteration with a planning session at the start and a review/demo at the end. This creates a repeatable rhythm so the team agrees what is in scope, what is not, and what “done” looks like.
3. Daily stand-up. Each developer states what they completed yesterday, what they are doing today, and any blockers. This prevents confusion, duplicated work, and hidden risks from surfacing too late.
4. Definition of Done. A work item is not complete until it is coded, tested, reviewed, and integrated. This prevents partially finished work from being counted as done.
5. Visible workflow board (requested → in progress → review → done). This gives the team a single view of every piece of work from request to completion and makes progress and bottlenecks obvious.
6. Sprint review and retrospective. The team reviews business value and the process itself. This prevents the same mistakes repeating and ensures the team learns and improves.

Together these guardrails create a repeatable process, make ownership clear, and give managers and developers a live picture of work from request to release.

=== Question 1.3 ===
A daily stand-up is a short operational meeting. It happens daily, usually at the start of the day, and focuses on progress, upcoming work, and blockers. It is meant to coordinate the team and remove immediate obstacles.

A sprint retrospective is a learning meeting held at the end of a sprint or iteration. It focuses on the team’s process: what went well, what went badly, and what to improve next time. It produces actions for improvement, not task status. The stand-up produces coordination; the retrospective produces learning and process change.

=== Question 2.2 ===
Encapsulation: Keep fields and internal state private and expose controlled operations. In the dispatch package, `Parcel` declares private fields such as `trackingNumber`, `senderName`, `recipientAddress`, `weightKg`, and `delivered`, and exposes getter/setter-style methods. This is encapsulation because callers cannot mutate state directly; the class controls validation and access.

Inheritance: A subclass extends a parent and reuses its behaviour while adding its own. `StandardParcel`, `ExpressParcel`, and `FragileParcel` all extend `Parcel`, which is the common base class. They inherit the parcel identity and validation logic and provide their own behaviour.

Abstraction: Hide unnecessary detail behind a common contract and use abstract concepts. `Parcel` is abstract and declares abstract methods `deliveryFee()`, `deliveryDays()`, and `serviceLevel()`. The subclasses implement those behaviour contracts without callers needing to know which parcel type they hold.

Polymorphism: Different subclasses can be treated through the same type and respond differently to the same method call. In `DispatchCentre`, a `List<Parcel>` can hold `StandardParcel`, `ExpressParcel`, and `FragileParcel`, and each one implements `serviceLevel()` or `deliveryFee()` differently while still being a `Parcel`.

Refactoring is changing the internal structure of code to make it easier to understand, modify, and maintain without changing its observable behaviour. It is different from a bug fix because a bug fix changes behaviour to correct an error, and different from a feature because a feature adds new behaviour. In `DeliveryRulesService`, the `canLoadOntoVehicle` method has a long chain of conditions and nested logic. That makes it hard to read and reason about. I would refactor it by extracting helper checks such as “is vehicle capacity okay”, “is the driver certified for fragile loads”, and “is the driver allowed to collect cash”, so the overall rule becomes clearer without changing any outcome.

`pom.xml` is Maven’s project configuration file. It tells Maven what the project is, which Java version to use, which dependencies to fetch, and how to build/package it. Without it, the team would need to manually compile code, resolve libraries, set compiler flags, and decide build steps on every machine and in the CI pipeline.

In this project, two things the `pom.xml` defines are:

2. Dependencies and plugins, including the SQLite JDBC driver and the assembly plugin that creates the runnable jar. Maven downloads the driver and packages the application into a jar-with-dependencies for distribution.

=== Question 5.4 ===
A `PRIMARY KEY` means “this column uniquely identifies each row, and it cannot be null.” A `UNIQUE` constraint means “no two rows can share that value,” but it is not necessarily the row’s identity column. For example, `tracking_no` must be unique among parcels, but the actual identity of the row is still the internal `id`.

`delivery_attempts` references `parcels.id` rather than `parcels.tracking_no` because `id` is a stable internal identifier that does not change, while tracking numbers are business data and may be subject to rules or correction. Using the surrogate key makes the foreign key simpler, more efficient, and less brittle than depending on a business value that might change or be reformatted later.

Server-side generation: the browser requests `/balances.html`, and the server fetches the account data, builds the full HTML page, and sends that HTML back. The work happens on the server, and the browser receives a complete page.

Client-side generation: the browser requests a shell page, then JavaScript fetches the balance data from an API and uses it to build the page in the browser. The work happens partly in the browser, and the browser receives the shell page plus data (usually JSON) rather than the final HTML.

An API endpoint is a URL that the server exposes for programmatic data access. It usually returns JSON because JSON is a lightweight, language-neutral data format that JavaScript can parse easily and use to update the DOM without reloading the page.
